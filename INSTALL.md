# PSC-CHIMERA installation

## Install

From the repository root, create and activate a virtual environment using the
commands for your shell.

### Windows PowerShell

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install .
```

### Linux / WSL

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install .
```

Use `python -m pip install -e .` for editable development or
`python -m pip install -e '.[dev]'` to add the development/test dependencies.
For GPU or ROCm use, install the platform-specific PyTorch wheel first using
the command generated by the official PyTorch installer, then install CHIMERA.

Run the optional environment diagnostic and check the installed command:

```console
python scripts/check_install.py
chimera --version
chimera --help
```

After installation, verify that imports and the CLI work independently of the
repository directory:

```powershell
chimera --version
chimera --help
```

## PyTorch / GPU

If you need a specific CUDA or ROCm build, install the platform-specific PyTorch
wheel first using the command generated by the official PyTorch installer, then
run `pip install -e .`. This avoids forcing one CUDA runtime onto every machine.

## Pretrained models

```bash
chimera models list
chimera models fetch esm2_t30_150m
chimera models verify --offline
```

Model downloads are explicit and are not performed by installation or package
imports. Set `CHIMERA_MODEL_CACHE` to select a cache directory. Asset identities,
upstream sources, licenses, and adapter limitations are recorded in
[`docs/pretrained_models.md`](docs/pretrained_models.md).

## Weight transfer

The repository treats pretrained models as **external artifacts**, not source
files. Copying a filename into `weights/` does not register or verify it.
Unmanifested files are not accepted by the identity-addressed model store.
Training resume checkpoints use Python serialization and must come from a
trusted source. For the implemented contracts and remaining limitations, see
[`docs/PRODUCTION_ENGINEERING.md`](docs/PRODUCTION_ENGINEERING.md).

Native adapters must use the matching upstream runtime and checkpoint. A file
digest alone does not establish architectural or semantic compatibility.

## Scientific implementation boundary

The local transport implementation is an SE(3) Schrödinger-bridge approximation
using a Brownian reference in a local Lie-algebra chart. It is not a claim of an
exact heat-kernel bridge on SO(3). Likewise, MC Dropout provides an approximate
epistemic posterior, and Expected Improvement assumes the scalar predictive
quantity is approximately Gaussian.

The implementation follows the core ideas of Schrödinger bridges, gradient
surgery, and direct preference optimization, including:

- Schrödinger bridge / stochastic optimal transport: entropy-regularized path
  measures with a reference diffusion process.
- PCGrad: project conflicting task gradients rather than comparing scalar loss
  magnitudes.
- DPO: optimize chosen-vs-rejected sequence log-probability ratios relative to a
  frozen reference policy.
- Bayesian uncertainty: distinguish MC epistemic variance from predictive
  aleatoric variance.
- Expected Improvement: use predictive standard deviation as `sigma`, not
  variance.

These methods remain approximations to the corresponding full research systems
and should not be interpreted as experimental validation of a biological design.
